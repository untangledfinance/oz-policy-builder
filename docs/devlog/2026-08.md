# OZ Policy Builder devlog, August 2026

Monthly update on the OZ Policy Builder, an SCF-funded toolkit that turns a
Soroban transaction you have already made into a policy an OpenZeppelin smart
account enforces on every later call.

The most useful thing we learned this month is not about our tool.

## Attaching a policy to a context rule changes who can act alone

A context rule with no policy requires the *full* signer set to approve. Attach
any policy and signer validation is deferred to that policy, so any single
signer on the rule can act alone.

So if you have a rule with two signers and attach a policy expecting "both must
approve", you get the opposite. Either signer acts by themselves. To require a
threshold you have to attach one, as a policy that counts signatures.

We verified both directions on testnet and mainnet. With a 2-of-2 threshold
attached, a lone signer is refused and the two-signer call passes. Without it,
on the same rule with the same two signers, the lone signer goes through.

One edge worth knowing: OpenZeppelin's threshold policy fixes the count at
install and is not told when the rule's signers later change, so adding a signer
would quietly turn a 2-of-2 into a 2-of-3. Our interpreter stores a hash of the
signer set at install and re-checks it on every call, so in that combination the
rule stops working instead of quietly meaning less. Stopping is the safe
direction, but it is still a surprise if you are not expecting it.

## Multiple policies on one rule compose as ALL-OF

Every attached policy must permit. This is what makes an OpenZeppelin
`spending_limit` attached beside a custom policy a real bound rather than a
bypassable one.

We tested it by putting two policy instances on one rule with predicates that
disagreed about the same call, and the refusing one decided the outcome. A
control rule carrying only the permitting policy allowed the identical call, so
the denial belonged to the second policy rather than to a malformed rule.

Both findings were settled by experiment on chain rather than read from
documentation, because getting either wrong would have inverted a
recommendation.

## What shipped

Ten releases of the core and the CLI and eleven of the MCP server, 0.3.0 through
1.0.0, all on npm as `@crediolabs/policy-synth`,
`@crediolabs/policy-builder-cli` and `@crediolabs/policy-builder-mcp`.

**A wider policy grammar.** Version 4 of the on-chain grammar added `or`, the
ordering comparisons `lt`, `gt` and `gte`, and a leaf that scales one argument
of a call so it can be compared against another. Before that a rule could say
"at most X" but not "at least X", and could not express a choice between two
shapes of the same action.

**Slippage floors, which the new leaf is really for.** You can now write "the
amount out must be at least 99% of the amount in". The floor is compared against
the call's own input rather than a fixed number, so one rule covers every trade
size instead of pinning the policy to a single trade. It is never inferred from
a recording, because a recorded rate is a price at one moment and freezing it as
policy would deny ordinary trades a week later. You state the ratio.

**Bounds on values nested inside a call.** Some protocols do not put the amount
at the top level. A Blend `submit` carries it inside a list of request structs.
A rule can now reach in and bind it, and it binds **every** entry plus the list
length, because bounding one entry leaves the others free and a caller simply
puts the spend in an unbounded one.

**Policies as data, not generated contracts.** The synthesiser emits a predicate
document that one immutable interpreter evaluates. A new combination of
constraints needs no deployment and no fresh audit. That was the design bet at
the start of the grant and it has held up.

## Decisions taken

**The confirmation step is the wallet signature.** Our MCP server returns an
unsigned transaction and never holds a key. We considered a separate confirm
call in the tool protocol and did not add one: the component that holds the key
is the right place to show a user what they are approving, and a second
confirmation ahead of that one adds a step without adding a guarantee. The
server stays stateless as a result.

**A dropped policy now fails loudly.** Our install builder used to skip a policy
kind it did not recognise, silently, so a caller attaching a spend cap could get
back a rule without one and no indication. A dropped policy means the
restriction is simply not there, so it raises an error instead. Worth checking
whether your own builders do the same, because the failure is invisible by
construction.

**Periods are ledger counts, not seconds.** The OpenZeppelin spend limit takes
`period_ledgers`. A "per day" cap is really a cap per 17,280 ledgers at roughly
five seconds each, so it is an approximation of a day and we report it as one
rather than restating it as exact.

## Open questions, and we would value input

**1. Would a `frequency_limit` primitive be useful to anyone else?**

There is no way to cap how *often* a key acts. A spend cap bounds how much: a
key capped at 100 a day can still make a thousand calls of 0.1. We have proposed
a `frequency_limit` policy upstream, modelled on `spending_limit`'s shape with a
ledger count and a call count:
[OpenZeppelin/stellar-contracts#858](https://github.com/OpenZeppelin/stellar-contracts/issues/858).

One property makes it cheaper than it first looks. `spending_limit` keeps a
history that grows with call volume, which is unbounded by the policy itself. A
frequency limit's history is bounded by the limit: once the count reaches the
cap the call is denied, so the stored vector can never exceed it.

The cost is still real. Counting calls means writing on every approved call, and
our interpreter deliberately writes nothing during a check, which is a large
part of why it is small and cheap to audit. That is why this belongs upstream,
in a policy that already pays for a write, rather than in our interpreter. If
you have a use case that needs frequency rather than amount, the issue is the
place to say so.

**2. Which smart-account-supporting wallets can handle an `add_context_rule`
transaction today?**

We build the install as an unsigned transaction and hand it to a wallet. We have
exercised that with Freighter. We decoded what we produce and it is an ordinary
Soroban `InvokeHostFunction` with ordinary authorisation entries and the
resource footprint already attached, so the receiving wallet does not have to
simulate anything itself. There is no custom field in it.

That says the format should not be the obstacle. It does not tell us which other
wallets have actually been pointed at one. If you maintain a wallet that
supports contract accounts, we would like to compare notes, and we will record
what we find in the
[developer guide](https://docs.untangled.finance/docs/OctoGate/account-permissioning/developer-guide).

**3. Is the any-of-N behaviour at the top widely understood?**

We expected all-of-N and were wrong, and it took an experiment to settle. Our
review card already carries a line about it: any rule with two or more signers
gets a note saying that any one of them may authorise a permitted call. A
single-signer rule is trivially any-of-one, so the note would be noise there.

If this is common knowledge among people building on the accounts package, the
useful fix is documentation rather than tooling. If it is not, other tools that
install policies may want a similar note. We are interested either way in
whether others have hit it.

## Where things stand

The three reference walkthroughs are installed on testnet with public receipts:
a capped yield-claim delegation, a capped subscription, and a bounded swap. The
synthesiser is replayed against 33 real mainnet transaction envelopes covering
26 distinct call shapes. An independent audit of the synthesiser and the
interpreter is in progress; findings will be published in the repository.

The interpreter is verified under protocol 28. Testnet is a protocol ahead of
mainnet at the moment, so the two-network end-to-end run is a free
forward-compatibility check: on 27 August the permit, deny and bypass-blocked
cases all passed on testnet in ledger 4366193 at `protocol_version` 28, and the
same three passed on mainnet in ledger 64151857 at 27. If you maintain a Soroban
contract and are not already running against testnet while it leads, it is worth
doing, because it costs nothing beyond the run you already have.

Questions and criticism welcome, particularly on the three above.
