## What was checked

All 12 harness checks passed:

| Check | Evidence |
|---|---|
| Deterministic derivation and namespace separation | Same inputs reproduce the address; changing Prime, network or version changes it. No fee-payer input participates in derivation. |
| Actual OZ account code | Live instance matches the earlier pinned OZ account WASM. |

| Salt tampering | Changing salt while retaining the original authorization fails. |
| WASM tampering | Changing to the existing test-venue WASM while retaining the original authorization fails. |
| Actual deployment | Fee-bump transaction succeeds on ledger, returning the predicted address. |
| Identity verification | Live deployed executable matches the expected hash and Symbol("prime") instance storage matches the selected Prime. |
| Duplicate deployment | RPC simulation rejects another creation at the same address with Storage/ExistingValue. |
| Reuse check | Read-only verification recognizes the existing adapter; no second deployment was submitted. |

Negative cases above are authenticated RPC simulations, not submitted failed ledger transactions. The successful activation is an actual confirmed transaction.

After completion, `--verify` independently re-read the transaction and live ledger entries, decoded the outer fee payer, inner source, CreateContractV2 deployer, salt, executable, constructor arguments and Prime authorization, and repeated the code/binding checks. It passed.

## Implementation detail established

The SDK's existing `counterfactualStellarContractId` algorithm works with Prime's C-address. Its source is copied with provenance into `scripts/execution-counterfactual.ts` for this reproducible experiment. The execution salt is separate from the existing NEAR-identity-based `primeStellarSalt`.

The creation authorization tree contains one `sorobanAuthorizedFunctionTypeCreateContractV2HostFn` context. The OZ diagnostic representation is `CreateContractWithCtorHostFn`, including the executable, salt and constructor arguments. Selecting owner rule 0 and constructing the account AuthPayload/delegated signer authorization works on the existing OZ WASM. No account upgrade or deployment factory was needed for this test.

The old execution harness's context walker assumed `contractFn()`; this new verification handles the creation variant explicitly. App/SDK integration must do the same. A caller cannot merely submit from the owner's G-address and omit Prime's authorization.

The deterministic address is independent of the sponsor. This test specifically proves sponsorship through a fee-bump envelope; it does not exercise every possible relayer/signing architecture.
